## 三、核心仿真引擎（FR-16）

### 3.1 实体数据结构（预分配结构化数组）

实体为**定长结构化数组**，所有实体（人/车）共用一张表，按 `kind` 区分，避免 8000 个 Python 对象带来的 GC 与内存开销。

```python
entity_dtype = np.dtype([
    ('id',        np.int32),    # 唯一 ID
    ('kind',      np.int8),     # 0=行人, 1=车辆
    ('src_node',  np.int32),    # 起点节点
    ('dst_node',  np.int32),    # 终点节点
    ('cur_edge',  np.int32),    # 当前所在边，-1=在节点上
    ('edge_pos',  np.float32),  # 沿边行进偏移（米）
    ('speed',     np.float32),  # 当前速度（m/s）
    ('active',    np.bool_),    # 是否在场
    ('wait_ticks',np.int32),    # 在节点等待计数（用于转向/排队）
])
```

`EntityPool` 负责预分配（`capacity=10000`）与槽位管理（复用释放槽，避免动态扩容），提供 `spawn / recycle / active_mask`。

### 3.2 向量化 tick 更新

每 tick 全部 active 实体一次数组运算，只有"到达/转向"的小子集进入 Python 分支：

1. **流入**：`FlowDataGenerator.sample(tick)` 拿到本 tick 新生实体 → `pool.spawn`。
2. **位移**：`edge_pos[speed>0] += speed[speed>0] * dt`（全数组广播）。
3. **到达/转向**：`edge_pos >= edge_length` 的实体（用布尔掩码提取），按 `cur_edge` 查询路径下一跳，更新 `cur_edge / edge_pos / speed`；到终点则 `active=False`。
4. **密度聚合**：`np.bincount(node_id_of_active, minlength=n_nodes)` → 每节点实时人数/车数。
5. **调控**：每 `check_interval` tick 调用 `JointRegulator.predict` 与 `GatePolicyController.predict`，把策略应用到门闸放行速率与资源分配。
6. **统计**：metrics 记录本 tick 密度、吞吐、平均速度、tick 耗时。

### 3.3 路径规划与移动

- **宏观路径**：实体生成时从 A 的 `ShortestPathFinder`（Dijkstra，按人流密度加权边权）或预计算路径表取得**边序列**，存于 `pool.paths[id]`（仅生成时计算一次）。
- **微观移动**：行人按期望速度沿边匀速；车辆走 `movement.py` 提供的跟驰骨架（C 在其上扩展 IDM/CAV）。`movement.py` 为可替换插件（见第七章）。

### 3.4 对外接口（引擎本身）

```python
class TickEngine:
    def __init__(self, topology, flow_generator, gate_policy=None,
                 joint_regulator=None, dt=1.0, max_capacity=10000, seed=42): ...
    def reset(self) -> TickEngine: ...                 # 复位到初始状态
    def step(self, tick) -> dict: ...                  # 推进一个 tick，返回本 tick 快照
    def run(self, n_ticks) -> SimulationResult: ...    # 连续运行 n 个 tick
    @property
    def density(self) -> np.ndarray: ...               # 当前全节点密度 (n_nodes, 2)（人/车）
    @property
    def state(self) -> dict: ...                       # 供调控器/外部读取的当前状态
```

> 引擎不实现 `fit/predict`（非算法类，是仿真器），但所有**算法类**（GatePolicyController / JointRegulator / FlowDataGenerator 的策略部分）强制 sklearn 风格，满足标准五。

### 3.5 实时密度字段（8.2 协作1 → B，字段定义）

引擎每个 tick 产出的实时密度快照（内存对象 + 导出记录），字段如下，8.2 上午冻结：

| 字段 | 类型 | 说明 |
|---|---|---|
| tick | int | tick 序号（= 秒） |
| timestamp | str | 模拟时间（HH:MM:SS） |
| node_id | str | 节点编码（与 A 拓扑一致） |
| people | int | 节点区域内人数 |
| vehicles | int | 节点区域内车辆数 |
| density | float | 综合密度 = people / 区域容量（0~1+） |
| level | str | 等级：low / medium / high / critical |

## 四、随机数据生成器 FlowDataGenerator（FR-17）

### 4.1 设计

按**时段密度曲线 + OD 矩阵 + 泊松到达**生成人/车流入计划，可配置密度与时段分布，支持"平时 / 高峰 / 超高峰"三种级别。

```python
class FlowDataGenerator:
    def __init__(self, n_people=5000, n_vehicles=300,
                 density_level='peak', peak_times=((8,9),(12,13),(18,19)),
                 od_matrix=None, random_state=42): ...
    def fit(self, X=None, y=None) -> FlowDataGenerator: ...   # 生成器无监督，返回 self
    def generate(self) -> FlowDataset: ...                    # 生成完整数据集（8.3 交付 D）
    def sample(self, tick) -> np.ndarray: ...                 # 引擎逐 tick 取流入实体参数
```

### 4.2 参数说明

| 参数 | 类型 | 说明 |
|---|---|---|
| n_people / n_vehicles | int | 计划总人数/总车数 |
| density_level | str | 平时 / 高峰 / 超高峰，对应密度强度倍率 |
| peak_times | tuple | 高峰时段列表，非高峰为平缓强度 |
| od_matrix | np.ndarray | 入口 → 热点区域（兴趣点）的概率矩阵，默认等概率 |
| random_state | int | 随机种子（可复现） |

### 4.3 输出数据集（8.3 → D 训练数据）

`FlowDataset` 含：

- `people.csv`：`id, birth_tick, src_node, dst_node, kind`（kind=0）
- `vehicles.csv`：`id, birth_tick, src_node, dst_node, kind, is_internal`（kind=1）
- `density_series.csv`：每 tick 每节点密度时间序列（供 D 训练密度预测模型、E 画曲线）

数据量以 8000 正式压测为准；首版（8.3）先出 4000 量级供 D 训练。

## 五、动态门闸控制算法（FR-19）

### 5.1 设计

根据实时人流密度自动调节门闸放行策略（开几道闸、放行速率上限、准入模式），使用**滞回控制**避免开关抖动。

```python
class GatePolicyController:
    def __init__(self, window_size=10, open_threshold=0.5, close_threshold=0.3,
                 max_lanes=4, min_lanes=1): ...
    def fit(self, history) -> GatePolicyController: ...   # 学习历史密度 → 自适应阈值
    def predict(self, density_now) -> dict: ...           # → {gate_id, mode, throughput_cap, n_lanes}
    def get_params(self, deep=True) -> dict: ...
    def set_params(self, **params) -> GatePolicyController: ...
```

### 5.2 predict 返回结构

```python
{
  "gate_id": "gate_north",
  "mode": "open" | "restricted" | "closed",
  "throughput_cap": 40,     # 单位 tick 放行人数上限
  "n_lanes": 2,             # 开闸数（1~max_lanes）
}
```

### 5.3 滞回逻辑

- 密度 > `open_threshold`（或学到的自适应阈值）→ 关闸/限流（mode=restricted，降低 `throughput_cap`）。
- 密度 < `close_threshold`（= `open_threshold` 的 60%）→ 开闸（mode=open，恢复放行）。
- 阈值可由 `fit(history)` 用 EWMA + 分位数自适应学习，避免拍脑袋定参数。

## 六、宏观-微观联合调控 JointRegulator（FR-18）

### 6.1 设计

宏观层识别密集区域（结合 A 的 PageRank/热度指标），按优先级把微观计算资源（如每区域更细的仿真/路径优化预算）分配到密集区；微观层反馈结果回写，调整宏观规划——形成**宏观→微观→反馈→宏观**闭环。

```python
class JointRegulator:
    def __init__(self, check_interval=10, budget_pool=100, decay=0.5): ...
    def fit(self, macro_cfg) -> JointRegulator: ...      # 学习拓扑+宏观热度配置
    def predict(self, state) -> dict: ...                # → {region_id: compute_budget, priority}
    def get_params(self, deep=True) -> dict: ...
    def set_params(self, **params) -> JointRegulator: ...
```

### 6.2 predict 返回结构

```python
{
  "regions": [
    {"region_id": "zone_canteen", "priority": 0.92, "compute_budget": 30},
    ...
  ],
  "global_plan": "focus_dense",      # 宏观策略标识
}
```

### 6.3 闭环逻辑

1. **宏观识别**：每个 `check_interval` tick，用当前密度 + A 提供的热度指标对区域排序。
2. **分配**：从 `budget_pool` 按优先级分配预算给密集区，闲置区预算按 `decay` 回收。
3. **微观反馈**：微观移动/路径优化结果（如某区域疏散效率）回写为区域成本修正项，下一次分配时纳入。
4. **差异化路径规划**：密集区内的实体切换为"微观精细路径"（局部绕行），非密集区沿用宏观 Dijkstra 结果——落实"两个层面采用不同路径规划算法"。

## 七、扩展性设计（FR-20）

### 7.1 插件化替换点

| 替换点 | 基类/接口 | 可替换实现 |
|---|---|---|
| 微观移动模型 | `movement.BaseMovement` | 匀速步行 / IDM / CAV 跟驰（C） |
| 路径规划 | A 的 `ShortestPathFinder` | Dijkstra / 密度加权 / 局部绕行 |
| 门闸策略 | `GatePolicyController` | 阈值 / 学习型 / 强化学习 |
| 数据生成 | `FlowDataGenerator` | 泊松 / 真实数据回放 |

接入方式：实现同一接口后经 `config.yaml` 指定类名即可，引擎代码零改动。

### 7.2 扩展功能清单（标准八加分）

1. **DB 回放**：把引擎输出快照落 MySQL（对接 B），支持"历史回放"模式。
2. **真实数据接入**：有真实闸机/客流数据时，生成器切换为数据回放模式。
3. **在线调参**：通过 `get_params/set_params` 在运行中调整门闸阈值与预算分配。
4. **多场景拓扑**：拓扑文件可替换（体育场/商场场景），引擎逻辑不变。

### 7.3 防恶意攻击/健壮性（要求七）

- 引擎输入严格校验（`check_array` 风格），拒绝非法密度/负速度。
- 参数白名单经 config 注入，不信任运行时字符串执行。
- 日志统一 `[时间戳][级别][模块.方法]`（附录 D），支持按天落盘，便于审计。

## 八、压力测试方案（NFR-01 / FR-20）

### 8.1 目标与分级

| 阶段 | 时间 | 规模 | 目的 |
|---|---|---|---|
| 预压 | 8.6 | 4000 人/车 | 先暴露瓶颈，为 8.7 留修复时间 |
| 正式 | 8.7 | 8000 人/车 | 验收（超出题目 3000 人要求） |

加压曲线：**1000 → 2000 → 4000 → 6000 → 8000**，每级 warmup 10 tick 后测 100 tick。

### 8.2 测试脚本（stress_test.py）

```python
def run_level(n_entities: int, n_ticks: int = 100) -> StressReport:
    # 1. 构造 FlowDataGenerator(n_people=n_entities, ...) + TickEngine
    # 2. 预热 10 tick（不计时）
    # 3. 正式计时：perf_counter 逐 tick、分模块（位移/转向/聚合/调控）计耗时
    # 4. tracemalloc/psutil 记录内存峰值与 CPU
```

### 8.3 核心指标与判定标准

| 指标 | 4000 预压门槛 | 8000 正式门槛 |
|---|---|---|
| tick 平均时延 | < 100 ms | < 100 ms |
| tick p95 时延 | < 300 ms | < 300 ms |
| 内存峰值 | < 2 GB | < 3 GB |
| 实体吞吐 | ≥ 20000 实体/s | ≥ 40000 实体/s |
| 正确性 | 无实体丢失、密度字段与人工抽样一致 | 同左 |

### 8.4 瓶颈定位流程

1. 分模块计时找出耗时占比最高模块（预期：转向/路径查询）。
2. cProfile 定位 Python 级热点（如生成器逐实体循环）。
3. 针对性优化优先级：
   - 转向/到达处理 → 掩码批量处理，减少 Python 分支；
   - 路径存储 → 边序列预计算，运行时只查索引；
   - 数据类型 → `float32` 减内存带宽；
   - 对象开销 → 杜绝每 tick 创建临时 dict/list。
4. 优化后复测，报告前后对比。

### 8.5 兜底策略（对齐《0-工作进度与安排.md》风险节）

- 4000 预压不达标 → 8.6 当晚修复，8.7 上午复核。
- 8000 无法全量达标 → 先保证"平均 tick 达标 + 无崩溃"，p95 指标以"降低运行时长换取"；答辩演示用 4000 量级保底，8000 以报告形式呈现。

### 8.6 交付物

《压力测试报告.md》：分级数据表 + 分模块耗时表 + 优化前后对比 + 结论（是否通过 8000 验收）。
