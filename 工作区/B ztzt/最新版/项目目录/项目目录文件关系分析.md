## 一、项目定位与总体架构

本项目是一个**园区安全智能调控仿真平台**：以园区路网为拓扑，用 tick 级（每秒一个 tick）离散事件模拟人群与车辆流动，叠加门闸/红绿灯调控策略，输出密度与流量的时序数据；再交由 AI 模块做拥堵预测与安全预警。

全项目可抽象为**三层 + 一条数据管道**：

```
┌─────────────────────────────────────────────────────────────┐
│ 第 1 层：根目录（配置源 + 数据源 + 数据生成）                    │
│   config.yaml  graph_data.yaml  flow_data_generator.py       │
│   文档/ 冻结JSON/ 地图.svg                                    │
└──────────────┬──────────────────────────────┬───────────────┘
               │ 注入 sys.path + 读配置         │ 读拓扑 YAML
               ▼                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 第 2 层：simulation/（仿真引擎包，成员 F 主导）                 │
│   config.py → topology.py → entities.py → engine.py          │
│   controller.py / movement.py / movement_cav.py              │
│   joint_regulator.py / metrics.py                            │
│   sender.py / csv_recorder.py / main.py / stress_test.py     │
│   macro_topo.py / macro_attractrank.py（宏分析，独立工具）      │
└──────────────┬───────────────────────────────────────────────┘
               │ 落盘：data/engine_timeseries.csv + data/json/
               ▼
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：test/（AI 预测与安全预警，另一成员主导）                 │
│   data_config.py → model.py（TSMixer/GRU + 异常检测）          │
│   service.py（SecurityService：读CSV→预测→预警→POST后端）       │
│   test.py / service_README.md / checkpoints/                 │
└─────────────────────────────────────────────────────────────┘
```

- **第 1 层**：工程事实来源（config.yaml 配置一切；graph_data.yaml 定义路网；flow_data_generator.py 生成 OD 出行需求）。
- **第 2 层**：核心仿真引擎，是一个可独立运行的 Python 包（`simulation/__init__.py`）。
- **第 3 层**：消费引擎落盘数据的 AI 服务，与引擎解耦（只依赖 CSV 表头，不 import 引擎代码）。

关键设计约束：**引擎不直接写盘、不改内部逻辑**，落盘由外部驱动循环（sender / csv_recorder / main）完成；AI 服务只认 CSV/JSON 数据契约，形成一条清晰的数据管道。

## 三、分层依赖关系详解

### 3.1 根目录层：配置源与数据源

| 文件 | 角色 | 被谁消费 |
|---|---|---|
| `config.yaml` | 一切可调参数的唯一入口 | `simulation/config.py`（唯一读取方），其余模块经 `get_config()` 间接获得 |
| `graph_data.yaml` | 路网事实来源：`nodes`(61)/`edges`(105)/`node_types`/`attractrank` 参数 | `simulation/topology.py` 的 `TrafficNetwork.from_yaml`；`simulation/macro_attractrank.py` 读 `attractrank` 块 |
| `flow_data_generator.py` | FR-17 出行需求生成器 + 常量中心（NODE_LIST/容量/OD/逗留时间） | `topology.py`（模块级 import 容量、节点类型）；`engine.py`（DWELL/WAIT 常量）；`main.py`（构造实例）；`simulation/macro_*` 间接 |

**根目录是"上游"**：第 2、3 层所有关键参数都源自这里，其中 `flow_data_generator.py` 与 `graph_data.yaml` 必须保持一致（两套节点清单顺序完全一致，见第七章校验结果）。

### 3.2 simulation/ 仿真引擎包

包内部依赖呈"装配"关系，核心在 `topology.py` 与 `engine.py`：

```
config.py（读配置+注入sys.path）
   │
   ▼
flow_data_generator 常量 ──► topology.py ──► movement.py / movement_cav.py
        （容量/类型/OD）        │  ▲              │
                              │  │              │
                              ▼  └──────────────┘
                        engine.py  ◄── controller.py（门闸/信号策略）
                              │  ▲
                              │  └── joint_regulator.py（联合调控）
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
   sender.py            csv_recorder.py          stress_test.py
   （JSON 落盘）          （累计 CSV 落盘）          （压测）
        └──────────────┬──────────────────────────┘
                       ▼
                  main.py（统一编排 CLI）
```

**关键依赖点：**

- `engine.py` 顶部 `import config` 是**副作用导入**——只为了触发 sys.path 注入与配置加载，不直接使用其符号。
- `topology.py` 在模块级 re-import `flow_data_generator` 的常量（TYPE_CAPACITY、DWELL_MIN/MAX、WAIT_MIN/MAX、TYPE_OD、NODE_LIST），使路网容量、逗留/等待时间与生成器保持单一来源。
- `controller.py` 的 `HysteresisPolicyController` 同时服务 `role="gate"`（门闸）与 `role="door"`（大门），`SignalPolicyController` 提供红绿灯信号周期；二者都被 `TickEngine` 构造注入。
- `movement.py` / `movement_cav.py` 实现 `BaseMovement` 抽象，`engine` 通过 `movement_class`（配置项）选择具体实现，实现移动模型可插拔。
- `sender.py` 与 `csv_recorder.py` 都实现**外部驱动循环**（`run_and_send` / `run_and_record`），在不修改 `engine.py` 的前提下逐 tick 调用 `engine.step()` 并落盘——这是架构上刻意为之的解耦。
- `macro_topo.py` / `macro_attractrank.py` 是**独立宏分析工具**：只 import `topology.TrafficNetwork`，不被引擎依赖；`macro_attractrank.py` 又依赖 `macro_topo.TrafficNetworkAnalyzer`。

### 3.3 test/ AI 预测与预警层

```
data/engine_timeseries.csv（引擎落盘产物）
   │ 读 CSV（路径在配置/启动参数中给定）
   ▼
data_config.py（列映射、枚举编码、特征工程参数 14 特征）
   ▼
model.py（DensityPredictor: TSMixer/GRU 密度预测 + CongestionDetector 异常检测）
   ▼
service.py（SecurityService：读CSV→建特征→predict→check_alerts→POST 后端）
   ▼
test.py（入口：from_config 指定 CSV 路径与后端地址，run_loop）
```

- `data_config.py` 定义 `RAW_COLUMNS`（13 列，**必须与 engine 的 CSV 表头逐一对应**）、枚举映射（level/gate/signal）、14 个特征列、归一化配置——是 AI 层与引擎层的**数据契约**。
- `model.py` 提供两种预测器（TSMixer-Lite 与 GRU）和三类异常检测（congestion/loitering/gate_anomaly），具备 sklearn 风格 fit/predict。
- `service.py` 的 `SecurityService` 是总装：读 CSV → 特征矩阵（n_ticks×n_nodes×14）→ 密度预测 → 异常检测 → 分类 → 登录后端 + POST `/api/v1/security/alerts/create`。
- `checkpoints/` 保存训练产物：`density_model/`（权重+config）、`preprocessor.json`（特征/节点清单/归一化参数）、`alerts.json`、`prediction.json`、`evaluation_report.json`。

## 四、核心数据流

### 4.1 静态导入依赖图（模块间 import 关系）

```
flow_data_generator ──► topology ──► movement / movement_cav
      │                    │
      │                    ▼
      └────────────► engine ◄── controller / joint_regulator
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
     sender           csv_recorder       stress_test
        │                 │
        └─────────────────┴──► main（编排一切）
                                    │
                                    └──► test/service（联动预测预警）
```

`macro_topo ──► topology`；`macro_attractrank ──► macro_topo`（独立分支，不进入引擎主链）。

### 4.2 运行时数据流（两条链路）

**链路 A：仿真主链路（引擎 → 落盘）**

```
FlowDataGenerator.generate() 生成 OD 出行
        │ sample(tick)
        ▼
TickEngine.step(t) 逐 tick：ingest → 移动 → 到达/信号 → 聚集 → 调控
        │ 返回快照 dict（tick/density/nodes/signals/gates/doors/joint_plan）
        ▼
sender.run_and_send（每 10 tick）→ data/json/engine_snapshot.json（同名覆盖）
csv_recorder.run_and_record（每 tick）→ data/engine_timeseries.csv（累计追加）
```

**链路 B：AI 消费链路（CSV → 预测 → 预警 → 后端）**

```
data/engine_timeseries.csv
   → service._read_csv（按 data_config 枚举映射）
   → _build_feature_matrix（n_ticks × 61 节点 × 14 特征）
   → DensityPredictor.predict（TSMixer/GRU，窗口 6 → 预测 3）
   → CongestionDetector.detect（拥堵/滞留/门闸异常）
   → 分类 + 构建预警 → POST 后端（demo_mode 下也构造演示预警）
```

### 4.3 配置传递链路

`config.yaml` 是唯一配置事实来源，经 `simulation/config.py` 的 `load_config/get_config` 单例缓存读取，并把 `paths.data_dir`、`simulation.*` 等散布到各模块：

- `engine.py` ← dt / max_capacity / enable_signals / vehicle_compliance / ped_compliance / movement_class
- `sender.py` / `csv_recorder.py` ← paths.data_dir / paths.csv_file
- `main.py` ← main.*（人数/车数/tick 数/天数/压测档位）
- `stress_test.py` ← max_capacity（预填充上限）

## 七、一致性校验结果与已发现的不一致

对跨文件的关键契约做了程序化核对，**重点结论如下**。

### 7.1 已校验通过（一致性 OK）

| 校验项 | 结果 |
|---|---|
| `graph_data.yaml` 节点顺序 vs `flow_data_generator.NODE_LIST` | **完全一致**（61 节点同序）——这是 `TickEngine._check_node_alignment` 的硬前提 |
| 生成器 NODE_LIST 节点数（61） vs YAML 节点数（61） | 一致 |
| YAML 边数（105） | 与拓扑构建一致 |
| `engine.SNAPSHOT_CSV_FIELDS`（13 列） vs `test/data_config.RAW_COLUMNS`（13 列） | 逐列对应（表头契约成立） |
| `sender.SNAPSHOT_JSON_FIELDS` vs CSV 表头 | 完全一致（JSON 契约 = CSV 契约） |
| `Topology.gate_nodes`（门闸）| 取 `is_gate & is_entrance`，实际生效 3 个入口闸机，与 YAML 一致 |
| `config.yaml` 拓扑路径相对解析 | 相对 config.yaml 所在目录（项目根），A 模块目录注入 sys.path 正常 |

### 7.2 已发现的不一致（潜在隐患）

| # | 不一致点 | 详情 | 影响 / 建议 |
|---|---|---|---|
| 1 | **信号灯节点集合三处不一致** | 生成器 NODE_LIST 标 `has_light=7`（3 闸 + 4 路口）；graph_data.yaml 标 `has_traffic_light=8`（6 路口 + 图书馆 + 体育馆，不含闸机）；`controller.DEFAULT_SIGNALS` 却定义 3 闸 + 4 路口（共 7）。**运行时实际只启用 4 个**（cross_zh_south/mid/north + rd_guanggong_1）——已由 `data/json/engine_snapshot.json` 证实：闸机 signal_status 为空，仅 4 个路口有相位。 | 文档声称"7 个信号节点"，实际 4 个。若成员 B/D 期望闸机也有信号，需统一事实来源（建议以 graph_data.yaml 为准，或明确闸机信号不启用）。 |
| 2 | **has_gate 集合不一致（功能上已规避）** | 生成器标 14 个 has_gate；YAML 只标 3 个入口闸机；`Topology.gate_nodes` 用 `is_gate & is_entrance` 取交集，**实际生效 3 个**，功能正常但两处标注口径不同。 | 属"标注冗余"，建议清理生成器中的闸机标记以消除误导。 |
| 3 | **冻结 JSON 与真实路网 ID 不符** | `相关的json文件(冻结)/交通网络.json` 使用 `zone_canteen`/`cross_1`/`diverg_1`/`gate_north` 等 ID，**在真实 61 节点网络中不存在**（真实为 zone_canteen_1 之类或英文 ID）。`红绿灯.json`/`门闸.json` 同理。 | 属接口契约示例，非运行时依赖；但对前端/后端联调有误导风险，建议按真实节点 ID 重出样例。 |
| 4 | **CSV 路径两处不一致** | `config.yaml paths.csv_file = 项目目录/data/engine_timeseries.csv`；而 `test/test.py` 硬编码 `D:\资料-study\6-QG暑期考核\1-QG园区\data\engine_timeseries.csv`（少了一层"项目目录"）。 | `test.py` 直接跑会找不到 CSV，必须经 `main.py run`（联动 service）才能对上。建议 test.py 改为读 config 或传参。 |

## 八、文件间关系速查（一句话版）

- **config.yaml** → 全局参数唯一入口，被 `simulation/config.py` 读取，间接注入所有模块。
- **graph_data.yaml** → 路网事实来源，被 `topology.py` 与 `macro_attractrank.py` 消费。
- **flow_data_generator.py** → 需求生成 + 常量中心，被 `topology.py`、`engine.py`、`main.py`、`macro_*` 消费。
- **topology.py** → 网络核心（DjShortCut 合并而来），被引擎、移动模型、宏分析共同依赖。
- **entities.py → engine.py**：实体池是引擎的"内存数据库"。
- **controller.py / joint_regulator.py → engine.py**：调控策略注入引擎，实现 FR-18/19。
- **movement.py / movement_cav.py → engine.py**：可插拔移动模型。
- **sender.py / csv_recorder.py**：不修改引擎的外部落盘器（FR-16 输出侧）。
