# 技术选型与架构说明

> 版本：v1.0 ｜ 日期：2026-08-02 ｜ 状态：草稿

## 一、后端技术选型变更

### 1.1 变更内容

| 维度 | 原方案 | 新方案 |
|------|--------|--------|
| 后端框架 | 未确定 | **Django + Django REST Framework** |
| 数据库 ORM | 未确定 | **Django ORM** |
| 认证 | 手写 JWT | **djangorestframework-simplejwt** |
| API 文档 | 手写 Swagger/Markdown | **DRF 自动生成 OpenAPI** |
| 安全防护 | 手写防注入/XSS/限流 | **Django 框架级保护 + django-ratelimit** |
| 数据管理后台 | 依赖前端 E 开发 | **Django Admin 内置** |

### 1.2 选型理由

1. FR-01~05 全部需求有框架级内置支持，无需手写
2. Django Admin 可直接覆盖 FR-02 数据管理需求，减少前后端联调压力
3. 今天（8.2）仍处于规划阶段，后端零代码、接口文档均为空白模板，切换零成本
4. 其他成员（A/C/D/F）的纯 Python 算法模块通过 import + Django ORM 直接对接，不受影响

### 1.3 风险与兜底

- **风险**：成员 B 无 Django 经验，学习时间仅 1 天
- **兜底**：Django 官方 Tutorial + DRF Quickstart 可在 4 小时内完成最小集学习；ModelViewSet 大幅缩减代码量，实际开发效率高于手写方案
- **兜底二**：若 Django 推进困难，8.3 傍晚前退回 Flask，接口文档已冻结不受影响

## 二、系统数据通道架构

### 2.1 总体分层

```
┌─────────────────────────────────────────────────────────┐
│                    前端 E（浏览器）                       │
│                         │                               │
│              REST API（唯一走 HTTP 的通道）              │
│                         │                               │
├─────────────────────────┼───────────────────────────────┤
│                    Django B                              │
│                  urls → views → serializers → models     │
│                         │                               │
│                  MySQL / PostgreSQL                      │
│                         │                               │
├─────────────────────────┴───────────────────────────────┤
│                                                         │
│   算法模块（全在同一个 Python 进程内）                     │
│                                                         │
│   A 宏观算法    C 微观仿真    D AI模型    F 仿真引擎      │
│     │              │           │           │             │
│     └──────────────┼───────────┼───────────┘             │
│            直接 import Python 对象互传                    │
│                                                         │
│   各模块也可以直接 import B 的 Django models 读写数据库    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.2 三种数据通道

| 通道 | 谁↔谁 | 方式 | 说明 |
|------|------|------|------|
| **① 函数直连** | 算法模块之间 | `from macro_topo import ShortestPathFinder` | 同进程 Python，不经过 HTTP |
| **② Django ORM** | 算法模块↔数据库 | `from api.models import AlertEvent` | B 定义 Model，其他人直接 import 读写 |
| **③ REST API** | 前端↔后端 | `GET /api/v1/realtime/density` | **浏览器只能走 HTTP，这是唯一用 API 的地方** |

### 2.3 具体举例

| 场景 | 走什么 | 伪代码 |
|------|--------|--------|
| D 拿到 F 生成的训练数据 | ① 函数直连 | `data = flow_gen.generate(3000)` |
| D 的检测结果入库 | ② Django ORM | `AlertEvent.objects.create(node_id=5, severity=3)` |
| E 的大屏查最新预警 | ③ REST API | `fetch('/api/v1/alerts?limit=10')` |
| C 的准入决策用 A 的最短路径 | ① 函数直连 | `path = finder.predict(src_node, dst_node)` |
| C 的准入决策用 D 的密度预测 | ① 函数直连 | `future = predictor.predict(timesteps)` |
| F 的仿真数据给 E 大屏展示 | ②→③ ORM入库→API查询 | F 写 DB → E 通过 B 的 API 读 |

## 三、关于"实时性"的说明

### 3.1 本项目"实时"的定义

本项目的"实时热力图""实时密度"指的是：**仪表盘展示仿真最新一帧数据**，不是毫秒级推送。

### 3.2 实现方式

前端每隔 1-3 秒通过 AJAX 轮询 `GET /api/v1/realtime/...`，Django 返回数据库最新行。对人眼即为"实时"。

### 3.3 不需要 WebSocket

| 场景 | 需要 WebSocket？ | 本项目有没有 |
|------|-----------------|------------|
| 聊天消息 | 是 | 无 |
| 股票行情 | 是 | 无 |
| 协同编辑 | 是 | 无 |
| 视频流 | 是 | 无 |
| **仪表盘轮询** | **否** | **✅ 本项目** |

### 3.4 性能

- 只有 1 个用户（管理员大屏）在轮询
- 8000 人/车压力落在 F 的仿真引擎上，不落在 Django 上
- 单次 Django API 查询 < 30ms
